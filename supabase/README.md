# Supabase persistence for the Frostpunk server

The realtime server (`apps/server`) can persist co-op games to Supabase. Without `SUPABASE_URL` it keeps everything in memory, so local development needs no account.

## Tables

| table | what | written by |
|---|---|---|
| `games` | one row per started game: room code, settings, status, outcome | server (service role) |
| `game_players` | seats of a game (guest id, display name, host flag, **hash** of the seat token) | server |
| `game_commands` | append-only log of accepted answers `{seat, pending_id, pick}` in order | server |
| `game_snapshots` | engine `serialize()` output every `PERSIST_SNAPSHOT_EVERY` commands, plus at start and end | server |

On boot the server loads every game with `status = 'playing'`, restores the latest snapshot and replays the command tail (or the full log if no snapshot is usable). Players then reconnect with their seat token.

## Security model

* RLS is enabled on all four tables.
* `anon` and `authenticated` have no write privileges and no write policies. Clients cannot write directly.
* `anon` and `authenticated` can read finished games (`status` won, lost or abandoned) through `games`, limited to summary columns. `config` (player names and guest ids) and the player, command and snapshot tables are not readable with the anon key.
* The service-role key bypasses RLS. It must only be set on the server (Render), never in the web build.
* `game_commands` rejects `UPDATE` and `DELETE` with a trigger (append-only). To delete a game, disable that trigger first (see the comment in `migrations/0001_init.sql`).

## Apply the schema

Either paste `migrations/0001_init.sql` into the Supabase SQL editor, or use the CLI:

```bash
supabase link --project-ref <ref>
supabase db push            # applies supabase/migrations/*.sql
```

The migrations are idempotent, so re-running them is safe. They are `migrations/0001_init.sql` (tables, RLS, append-only trigger) and `migrations/0002_service_role_grants.sql` (explicit grants for the server's `service_role`; a no-op on a standard Supabase project). Apply both, in order.

To check the SQL without a Supabase account, run `tests/pglite_check.mjs` (PostgreSQL in WASM, see `tests/README.md`).

## Server configuration

| variable | default | notes |
|---|---|---|
| `SUPABASE_URL` | unset | e.g. `https://<ref>.supabase.co`. Unset means in-memory mode. |
| `SUPABASE_SERVICE_ROLE_KEY` | unset | server secret. Set together with `SUPABASE_URL`. |
| `PERSIST_SNAPSHOT_EVERY` | `10` | commands between snapshots |
| `PERSIST_ATTEMPTS` | `10` | tries per write, with exponential backoff (0.5 s to 30 s). After the last try the write is dropped and logged; the game keeps running. Watch `persistFailed` on `/health`. |
| `MAX_ROOMS` | `200` | rooms held in memory |
| `MAX_CONNECTIONS` | `1000` | open WebSockets; extra connections get HTTP 503 |
| `ABANDON_GAME_MINUTES` | `1440` | a live game with no player connected for this long is saved as `abandoned` and unloaded |

## Idempotent writes

Every write is safe to repeat. Game ids are generated by the server, so `games` inserts are upserts on `id`. Players, commands and snapshots are upserts on their primary keys (`ignoreDuplicates` for players and commands, so a retry after a lost response is a no-op). This is what lets the server retry a write without creating duplicates. A command that was already stored is never overwritten.

## Seed data (local only)

`seed.sql` adds one finished sample game with a fixed id. It is loaded by `supabase start` and `supabase db reset` (see `[db.seed]` in `config.toml`). It is idempotent (`on conflict do nothing`). Its player token hashes are placeholders, so no live seat can resume it. `supabase db push` does not load it.

## Reading finished games from the web client

```ts
const { data } = await supabase
  .from('games')
  .select('id, room_name, scenario, society, difficulty, mode, status, round, end_reason, finished_at')
  .in('status', ['won', 'lost'])
  .order('finished_at', { ascending: false })
  .limit(20);
```

## Smoke test

1. Apply the migration.
2. Start the server with `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` set.
3. Create a room, start a game, answer a few decisions.
4. In the SQL editor: `select status, command_count from games order by created_at desc limit 1;` and `select count(*) from game_commands;`.
5. Restart the server. The game should come back: resume with the same seat token.
